# Phase 4 — DevOps & Cloud Deployment: Design

## Architecture

Two deploy targets behind one GitHub Actions pipeline: a static frontend served from S3 via
CloudFront, and a containerized backend running on ECS Fargate behind an Application Load
Balancer, reading from a managed RDS Postgres instance. Secrets (`JWT_SECRET_KEY`, database
credentials) live in AWS Secrets Manager and are injected into the ECS task at launch — never
baked into the image, never committed to the repo. Application logs go to `stdout`/`stderr`,
captured automatically by CloudWatch Logs. GitHub Actions authenticates to AWS via an
OIDC-federated IAM role rather than long-lived access keys.

Local Docker Compose remains the only non-production environment; this phase does not
duplicate the stack into a second AWS "dev" environment.

## Decisions

| #   | Decision                                                                                                        | Status  | Rationale                                                                                                                                                                                                                                                                                   |
| --- | --------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Cloud platform: AWS                                                                                             | Decided |                                                                                                                                                                                                                                                                                             |
| 2   | Backend hosting: ECS Fargate + Application Load Balancer                                                        | Decided | Broader, more transferable concept set than App Runner (VPC, security groups, service networking) — chosen deliberately for learning value over setup speed.                                                                                                                                |
| 3   | Frontend hosting: S3 + CloudFront                                                                               | Decided | Static build with no server-side rendering; a container would pay for compute to serve files.                                                                                                                                                                                               |
| 4   | Database: RDS for PostgreSQL (managed)                                                                          | Decided | A containerized database loses automated backups/patching on every task restart.                                                                                                                                                                                                            |
| 5   | Container registry: ECR                                                                                         | Decided |                                                                                                                                                                                                                                                                                             |
| 6   | Secrets: AWS Secrets Manager                                                                                    | Decided | Resolves the Phase 3 leftover — `JWT_SECRET_KEY` moves out of `.env.example` entirely.                                                                                                                                                                                                      |
| 7   | Logging: stdout/stderr → CloudWatch Logs                                                                        | Decided | Resolves the Phase 3 logging gap via the platform rather than a hand-rolled logging module.                                                                                                                                                                                                 |
| 8   | Environments: one AWS production environment; local Docker Compose is dev                                       | Decided | Avoids duplicating the full stack for a capstone-sized project.                                                                                                                                                                                                                             |
| 9   | CI/CD trigger and steps                                                                                         | Decided | Push to `main` → test → build & push image → run migrations → build & sync frontend, invalidate CloudFront → update ECS service → smoke-test.                                                                                                                                               |
| 10  | VPC/subnet layout: public subnets for ECS tasks, security group scoped to ALB only, no NAT gateway              | Decided | A NAT gateway has an ongoing cost and adds complexity the task has no outbound-internet need to justify.                                                                                                                                                                                    |
| 11  | No custom domain/TLS — use AWS-default URLs (ALB, CloudFront)                                                   | Decided | Route 53 + ACM can be added later; not load-bearing for demonstrating the pipeline.                                                                                                                                                                                                         |
| 12  | `JWT_SECRET_KEY` generated once, stored directly in Secrets Manager by hand                                     | Decided | A rare, one-time action — automation isn't warranted.                                                                                                                                                                                                                                       |
| 13  | Infrastructure provisioned via AWS Console first; Terraform written afterward to codify it                      | Decided | Console-first builds an intuition for what each resource is; Terraform afterward codifies something already understood rather than starting from the abstraction.                                                                                                                           |
| 14  | Deployed app pre-populated with dedicated, freshly-authored demo data — never migrated from local dev/test data | Decided | Local data includes known test credentials and mutation-testing artifacts, unsuitable for anything reachable outside the developer's machine.                                                                                                                                               |
| 15  | Seed script runs once, by hand, after migrations — not wired into CI/CD                                         | Decided | Same one-time-action reasoning as #12; running it on every deploy would duplicate rows or need reset logic that isn't needed yet.                                                                                                                                                           |
| 16  | GitHub Actions authenticates to AWS via an OIDC-federated IAM role, not long-lived access keys                  | Decided | Strictly better practice than storing static credentials as GitHub secrets, with no real downside at this scale.                                                                                                                                                                            |
| 17  | Backend dependencies pinned to exact versions via `pip freeze`, not `pip-compile`/Poetry                        | Decided | Closes a gap T-DO-1 surfaced: unpinned `requirements.txt` let the built image resolve newer versions than the dev venv, so two builds a month apart would differ. `pip freeze` solves it without introducing a new dependency-management tool for a problem this size doesn't need one for. |
